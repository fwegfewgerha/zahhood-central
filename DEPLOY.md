# Deploying Zah Hood Central

Two paths, both covered here.

- **Free, no card** — Render free plan, with Litestream keeping the database
  alive. This is the current plan.
- **Paid, later** — Fly.io with a real volume. `fly.toml` is already written.

Do step 1 either way. Claiming the domain first is what makes moving between
hosts painless later.

---

## 1. Claim the domain first

Setting `BASE_URL` once and never changing it means you can switch hosts
without touching Discord or signing anybody out.

1. Fork <https://github.com/is-a-dev/register>
2. Create `domains/zahhood.json`:

```json
{
  "owner": {
    "username": "YOUR_GITHUB_USERNAME",
    "email": "YOUR_EMAIL"
  },
  "record": {
    "CNAME": "zahhood-central.onrender.com"
  }
}
```

3. Open a pull request. Usually merged within a day or two.

`zahhood.is-a.dev` was free when this was written. If it has gone, try
`zah-hood`, `zahhoodcentral` or `zahhood-central`.

# Free path: Render + Litestream

## Why Litestream is here

Render's free plan gives you **no persistent disk**. The container's
filesystem is wiped on every deploy, every restart, and every idle
spin-down. A plain SQLite file would take your bans with it.

Litestream streams every write to object storage as it happens, and the
container restores the latest copy on boot. The disk still gets wiped; the
data comes back.

## 2. Create the storage bucket (Supabase — free, no card)

1. Sign up at <https://supabase.com> and create a project
2. **Storage → Create bucket**, name it `zahhood-db`, keep it **private**
3. **Project Settings → Storage → S3 Access Keys → New access key**
4. Copy the access key, the secret, and the S3 endpoint

The endpoint looks like `https://<project-ref>.supabase.co/storage/v1/s3`.

Your `REPLICA_URL` is then:

```
s3://zahhood-db/prod?endpoint=<project-ref>.supabase.co/storage/v1/s3&region=us-east-1
```

Note there is no `https://` inside the `endpoint=` part.

Cloudflare R2 or Backblaze B2 work identically if you ever add a card.

## 3. Push the repo to GitHub

Render deploys from a repository.

```bash
git remote add origin https://github.com/YOUR_USERNAME/zahhood-central.git
git push -u origin master
```

`.env` and `data/` are gitignored, so nothing secret goes up.

## 4. Create the Render service

1. <https://dashboard.render.com> → **New → Web Service**
2. Connect the repository
3. Render reads `render.yaml` and picks **Docker**, **free plan**
4. Before the first deploy, set the variables marked "set in dashboard":

| Variable | Value |
|---|---|
| `BASE_URL` | `https://zahhood.is-a.dev` |
| `DISCORD_REDIRECT_URI` | `https://zahhood.is-a.dev/auth/discord/callback` |
| `DISCORD_CLIENT_ID` | from your `.env` |
| `DISCORD_CLIENT_SECRET` | from your `.env` |
| `DISCORD_GUILD_ID` | `1521776473365807184` |
| `GIN_DISCORD_ID` | `504285424462856192` |
| `REPLICA_URL` | the `s3://...` line from step 2 |
| `LITESTREAM_ACCESS_KEY_ID` | Supabase access key |
| `LITESTREAM_SECRET_ACCESS_KEY` | Supabase secret |

`SESSION_SECRET` is generated by Render automatically. Leave it alone — it
must stay stable or everyone gets signed out on each deploy.

Leave `OWNER_DISCORD_ID` unset until you have somebody to make Game Owner.

## 5. Point Discord at the live URL

Developer Portal → your app → OAuth2 → **Redirects**, add:

```
https://zahhood.is-a.dev/auth/discord/callback
```

Keep the localhost entry too, so local development still works.

## 6. Add the custom domain on Render

**Settings → Custom Domains → Add** `zahhood.is-a.dev`. Render issues the
certificate once the is-a.dev CNAME has propagated.

## 7. Deploy, and read the logs

The startup output should show, in order:

```
[boot] replication target: s3://zahhood-db/prod
[boot] no local database - restoring from the replica...
[boot] nothing to restore - this looks like a first run. Starting fresh.
[boot] starting server under litestream replicate
  ...
  All security checks passed.
```

---

## 8. Verify replication actually works — do not skip this

Litestream failing quietly looks exactly like Litestream working. Prove it
once, now, while there is nothing to lose:

1. Sign in at `https://zahhood.is-a.dev`. You are whitelisted and
   `GIN_DISCORD_ID` matches you, so you arrive as Gin.
2. Do something that writes: whitelist a test Discord ID on the
   **Access & Security** page.
3. In Render, hit **Manual Deploy → Clear build cache & deploy**. This wipes
   the disk completely.
4. When it comes back, sign in and check the whitelist entry is still there.

If it survived, replication works. If it did not, the logs from step 7 will
say why — usually wrong credentials or a malformed `REPLICA_URL`.

Re-check this after any change to the storage credentials.

---

## Backups on top of replication

Replication protects against the disk being wiped. It does **not** protect
against somebody deleting the bucket, or against a bad write you want to
undo. Keep real backups too:

```bash
npm run backup
```

Writes a timestamped snapshot to `data/backups/`. Safe to run against a live
server. On Render, use the shell in the dashboard.

Worth doing before anything risky. The whole database is one file.

# Paid path: Fly.io, later

When you can add a card, Fly gives you a real volume and Litestream becomes
optional.

```bash
fly apps create zahhood
fly volumes create zahhood_data --region iad --size 1
fly secrets set DISCORD_CLIENT_ID=... DISCORD_CLIENT_SECRET=... \
  SESSION_SECRET=... GIN_DISCORD_ID=... DISCORD_GUILD_ID=... \
  BASE_URL=https://zahhood.is-a.dev \
  DISCORD_REDIRECT_URI=https://zahhood.is-a.dev/auth/discord/callback
fly deploy
fly certs add zahhood.is-a.dev
```

Leave `REPLICA_URL` unset and the entrypoint skips Litestream entirely,
running straight off the volume. Or set it and keep replication as a live
off-site backup — that is the better setup once you are paying.

To carry your data over: `npm run backup`, then upload the file to
`/data/zahhood.db` with `fly sftp shell` and restart.

Then repoint the `zahhood.is-a.dev` CNAME from Render to `zahhood.fly.dev`.
Because `BASE_URL` never changed, Discord needs no edits and nobody is
signed out.

## Things to watch

**One instance only.** The database is a file. Two instances would each get
their own copy and your data would split in two. Do not scale out.

**Render free sleeps after 15 minutes idle.** The first visit then takes
roughly a minute while it wakes and restores. Once your game is connected and
heartbeating every 15 seconds it never idles, so this stops mattering.

**Keep `SESSION_SECRET` stable.** Changing it invalidates every session.

**Litestream 0.5 is recent.** The config format changed from 0.4. If you
follow an older guide online it will not match `litestream.yml` here.
